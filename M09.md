Date: 2026-10-16. Branch: `milestone/m09-first-run-validation`.
Work in progress: authenticated/native and hosted evidence is still being collected.
No merge to main or release is authorized or performed.

## Journey audit and UX changes

M08 required already authorized/signed-in users to traverse installation and
sign-in pages, continue after repository selection, acknowledge generic
permissions, check readiness and then open another readiness page. Settings-first
setup also repeated navigation when returning to a saved issue.

M09 starts directly from **Run with AI** in a saved issue. **Find installation**
checks the existing state and selects the next missing requirement. Discovered
installation authorization advances after the existing identity/capability/auth
checks. Existing authorization and sign-in skip their completed pages. Selecting
an authorized Git folder advances directly to permissions. Permission review
opens the existing exact task preview directly. The generic acknowledgement and
separate readiness page were redundant with the existing exact execution approval
and have been removed; Claude's separate per-run host-risk consent is unchanged.
**Back** retains access to earlier steps and provider login.

A persistent summary reports **Installed**, **Signed in**, **Repository connected**
and **Ready to run**. This summarizes point-in-time authorization/sign-in state;
preview still rejects dirty/ineligible repositories, executable changes and policy
restrictions. It cannot promise network access or provider credits. Settings-only
setup explicitly asks users to choose a repository from a saved issue rather than
claiming full task readiness.

Installation help opens automatically only when no candidate is found. Paths and
explicit trust authorization remain visible; SHA-256 and prerequisite diagnostics
are optional advanced details. Plain-language step names replace internal state
names. A successful explicitly initiated browser login triggers an automatic
status recheck. Unknown/failed/cancelled status retains explicit retry/recheck.
Known installation directories and Codex's absolute installation-directory override
are reserved before bounded PATH scanning; duplicate PATH entries no longer
consume the search budget. Discovery never executes candidates or package managers.

## Local instrumentation and measurement method

`onboarding_metrics.py` is test-only instrumentation. It records numeric action
counts, monotonic elapsed seconds, errors/recoveries and seven allowlisted stage
names. It never records prompts, file paths, credentials, account identifiers or
provider output. There is no production telemetry or new persistence. Native
screenshots and logs stay in temporary local artifact directories; CI uploads only
numeric onboarding evidence alongside the existing package diagnostics.

Action counts cover named UI clicks/form fills, not every native keystroke or
accessibility polling request. Stage elapsed times include harness waits, provider
checks and OS dialogs and must not be presented as human first-user study times.
Simulated and authenticated-Codex evidence have separate labels. Real-provider mode
requires an additional explicit approval flag, an installed CLI and an existing
session; it creates exactly one disposable task and never opens a new login.

Actual measured results will be recorded here after the final native runs.

## Security review

UI → coordinator → typed IPC → Rust service/repository boundaries are preserved.
No migrations, dependencies, credentials, new capabilities, general opener/shell/
filesystem IPC, installer execution or automatic task execution are added.
Executable trust still requires explicit authorization of a canonical digest-bound
candidate or native picker selection. Existing expiring/single-use prompt approval,
launch-time identity/HEAD/policy revalidation, provider-specific Claude consent,
process supervision, queue dispatch and manual integration remain authoritative.
Recommended settings preserve required OS isolation; unavailable isolation fails
closed. Worktrees remain working copies, not OS security sandboxes.

The existing fixed `codex login` / `codex login status` and `claude auth login` /
`claude auth status` interfaces were rechecked against the
[official OpenAI command documentation](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
and [Claude CLI reference](https://code.claude.com/docs/en/cli-reference).
No interactive credential collection or undocumented browser deep link was added.

## Remaining friction and next steps

Native provider installation remains a deliberate manual action. Unsupported
wrapper-only installations and changed GUI PATHs retain the native picker/restart
fallback. Unknown CLI/auth interfaces fail closed. Dirty, unborn, detached,
submodule or tracked-symlink repositories still require user preparation. Browser
flows requiring interactive fallback input still need provider-owned terminal
login. No actual browser-login success with real credentials is claimed.

Human first-user timing studies, clean-machine signing/trust and whole-provider OS
containment remain separate work. Final authenticated and platform evidence must
be recorded before declaring the milestone complete.
