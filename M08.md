## Implemented functionality and UX flows

Guided setup is available in Agent settings and through a prominent **Run with AI**
action on eligible saved issues. The six steps cover provider choice, installation
and executable authorization, sign-in, project repository connection, conservative
permissions and first-task readiness. Status text, native labelled controls,
keyboard navigation, Radix focus trapping/Escape and actionable errors with optional
technical diagnostics support recovery. See [AI onboarding](docs/AI-ONBOARDING.md).

Rust detects absolute PATH entries, documented native provider locations, both
Homebrew prefixes, per-user WinGet portable links and Codex's documented
install-directory override. It canonicalizes,
hashes and deduplicates at most 16 candidates without executing discovered files.
Windows requires `.exe`; shell wrappers remain unsupported. Explicit authorization
uses a five-minute, provider/path/SHA-256-bound token held only in Rust memory,
then existing executable/capability verification. A native picker handles custom
installations. Missing Git/Node/npm file presence is reported without executing
untrusted prerequisites. Official OS-specific guides and optional copyable
Homebrew/WinGet commands leave installation to the user.

Authentication status uses documented Codex/Claude interfaces after authorization,
with explicit authenticated/unauthenticated/unavailable/unknown states. An explicit
login action opens the provider's browser flow via a supervised fixed-argument CLI
process, with cancellation, 180-second/16-KiB limits and no retained login output.
No credentials or private auth files are collected. Terminal fallback is described
for browser failures and interactive-only provider login modes.

The issue flow checks repository authorization and uses the existing native folder
picker. Optional recommended limits (one process, 600 seconds, 65,536 bytes and
provider conservative policy) preserve a previously required OS-isolation setting.
The explanation explicitly says worktrees are not OS sandboxes. Completing setup
opens the existing exact generated prompt approval dialog. Separate Claude consent,
single-use final execution approval, worktree creation, coordinator, progress,
cancellation, result review and manual integration are preserved.

## Security review

UI → feature coordinator → typed IPC → Rust command/service → existing SQLite
repository boundaries remain intact. No migration, credential persistence, arbitrary
shell/path/URL execution endpoint, capability or CSP expansion is introduced.
Two provider enums map to fixed official HTTPS installation guides. Discovery is
informational; authorization checks digest/path before and after bounded probes.
New scan tokens and login state are ephemeral and do not survive restore/restart.
Installed provider bytes still need user trust; hashing does not authenticate a
publisher or eliminate same-user replacement races.

Task setup cannot approve/start a run, grant Claude consent, enable privilege
escalation or silently remove an OS isolation requirement. Provider output remains
inert text; log redaction and existing provider-level restrictions retain their
limitations. Login uses the existing process supervisor/environment allowlist;
no inherited API keys are forwarded. Provider/browser authentication remains
provider-owned. OS-launched browser sessions can remain open after CLI cancellation.
Worktrees share Git metadata and are not whole-provider OS security sandboxes.

## Remaining friction and M09 recommendations

Installation still requires following an official provider guide and restarting
Forma if the OS PATH changed after launch. Custom installations retain a native
picker fallback. Unknown authentication output and incompatible security flags
fail closed. CLI browser flows that require interactive fallback input must be
completed in a terminal; Forma never collects those codes. A reported authenticated
session cannot guarantee credit availability or network access. Existing dirty,
unborn, detached, symlinked or submodule repositories need manual preparation.
Linux native onboarding is verified with a compiled fixture. Native Windows/macOS
onboarding and authenticated real-provider browser login/inference remain
unverified. Existing M07 release signing, platform trust and beta
acceptance blockers are not resolved by onboarding.

M09 should prioritize native first-user studies on each target, more documented
provider status versions, interactive login handoff without credential collection,
stronger externally managed OS containment, generated IPC contracts and existing
release trust/clean-machine acceptance gates. Automatic installation, credential
collection, automatic task approval and automatic integration remain excluded.
